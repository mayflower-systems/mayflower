dead simple and very portable models and utility functions for reading the "Reward Clearing" program.

This library is a straight-forward "wrapper" around the auto-generated client "@mayflower-sys/reward-clearing-sol-client" (in "reward-clearing/sol-programs/ts").

A "model" inside here is a human- & machine-friendly wrapper around the auto-generated models. For example, deserialized Q64x64 get converted to a nice "BigDecimal". And then 3rd-party programs that consume this friendly SDK can convert BigDecimal into whatever they want.

The "models" are pseudo-branded types in order to make the code very easy to read and reason about.

Each "model" module should have their corresponding "to/from" the autogenerated datatypes in the "reward-clearing-sol-client". These are just plain functions.

```ts
// EpochTerms.ts

import {EpochTerms as EpochTermsAccount } from "@mayflower-sys/reward-clearing-sol-client"
import { BigDecimal } from "./BigDecimal"

export interface EpochTerms {
    rampBonusSlope: BigDecimal
    exitPenaltyExponent: number
}

export const toAccount = (x: EpochTerms): EpochTermsAccount => { ... }
export const fromAccount = (x: EpochTermsAccount): EpochTerms => { .... }
```

The simplicity of this pattern will make it a very easy layer to build upon. This is will be a "pure functional" library that exposes functions that operate on pure data.

For example:

```ts
// EpochTerms.ts

...
export type RampBonusParams = {
  start: UnixTimestamp,
  now: UnixTimestamp,
  duration: number
  rampBonusSlope: BigDecimal,
}

export const rampBonus = (p: RampBonusParams): number => { ... }

// maybe this is ergonomic?
export const rampBonusFromModels = (e: Epoch, et: EpochTerms, now: UnixTimeStamp): number => {...}
```

The point is: pure functions are easy to compose with.

This library will be what is used by application developers. They fetch account data from Solana, use the generated client to deserialize them, and then can create these friendly, hand-written SDK objects.
